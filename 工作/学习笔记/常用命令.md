
##  1.设置主机名(主机名不能有下划线)
```bash

#临时生效
hostname NAME

#持续生效
hostnamectl set-hostname NAME

``` 

 
### 2.配置 hosts
是在 /etc/hosts 文件中添加一条记录，把当前服务器的所有IP地址和主机名绑定在一起。
```bash
cat >> /etc/hosts <<EOF
$(hostname -I)   ${hname}
EOF
```


## 3.su - dnet 与 sudo su - dnet 的区别

两者最终都是「以 dnet 用户身份启动一个登录 shell（login shell）」，
但**身份来源、认证方式、审计轨迹**完全不同。

### 3.1 先拆开看每条命令做了什么

| 片段 | 含义 |
|------|------|
| `su - dnet` | 直接运行 `su`，切换到 dnet，并加载 dnet 的登录环境（`-` = `--login`，等价于 `su -l`） |
| `sudo su - dnet` | 先用 `sudo` 以**当前用户+sudo 授权**拿到 root 权限，再在这个 root 下执行 `su - dnet` |

关键点：`sudo` 包的是「谁来授权切换到 root」，而 `su - dnet` 这一步在两条命令里**行为一致**。

### 3.2 核心区别对比

| 维度 | `su - dnet` | `sudo su - dnet` |
|------|-------------|------------------|
| **认证凭据** | 需要**知道 dnet 用户的密码**（root 切普通用户除外，root 切任何人免密） | 需要**当前用户的 sudo 密码**（通常是你自己的登录密码，跟 dnet 密码无关） |
| **所需权限** | 要么你是 root，要么你得有 dnet 的密码 | 你自己的账号要在 `/etc/sudoers` 里被授权 |
| **执行身份（euid）** | 由 `su` 直接 setuid 到 dnet | `sudo` 先提权到 root，再由 root 降权到 dnet，最终 shell 仍是 dnet |
| **审计/日志记录** | 默认不会在 `sudo` 日志里留下记录，谁操作的较模糊 | 会被 `sudo` 记录（时间、来源 IP、操作者、命令），便于追责 |
| **环境初始化** | 加载 dnet 的 `~/.bash_profile`、`~/.bashrc`、登录环境（`$HOME`、`$PATH` 等） | 同样加载 dnet 登录环境（因为最终还是 `su - dnet`） |
| **典型报错** | `su: Authentication failure`（dnet 密码错） | `xxx is not in the sudoers file`（当前用户没 sudo 权限）/ `Sorry, try again`（sudo 密码错） |

### 3.3 什么时候该用哪个

- **生产环境 / 多人协作 / 需要留痕**：优先 `sudo su - dnet`。操作可追溯，且不用把 dnet 密码散发给所有人。
- **你是 root，或你明确知道 dnet 密码、且临时快速切换**：`su - dnet` 更直接。
- **最佳实践**：实际上更推荐直接用 `sudo -i -u dnet`（或 `sudo -u dnet -i`），语义更清晰——「以 dnet 身份启动登录 shell」，且同样有 sudo 审计：
  ```bash
  sudo -i -u dnet      # 等价于 sudo su - dnet，但少一层 su 包装
  ```

### 3.4 一个容易混淆的点

- `su dnet`（**没有** `-`）：只切换用户，**不加载登录环境**，沿用当前 shell 的环境变量（比如 `$PATH` 可能还是上一个用户的）。生产排障时常因此踩坑（命令找不到、配置读不到）。
- `su - dnet`（**有** `-`）：完整登录环境，等价于重新登录 dnet。
- 运维场景默认加 `-`，避免环境变量污染。

### 3.5 记忆口诀

> `su` 要**对方密码**，`sudo` 用**自己授权**；
> 想留痕用 `sudo`，想干净环境加 `-`。
